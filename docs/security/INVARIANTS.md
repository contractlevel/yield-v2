# Yieldcoin V2 Invariants

<!-- @review reconsolidate with tests and update sibling docs -->

## Purpose

This document is the canonical invariant catalogue for the Yieldcoin v2 EVM
contracts in `evm/src/`.

Each property states the behavior to preserve, the boundary where it holds, and
the intended verification method. Tests should reference these IDs in test
names, assertion labels, or failure messages.

## Methodology

Invariants hold at transaction boundaries after successful top-level calls.
Failed transactions preserve prior state through EVM atomicity and do not
violate invariants. A caught downstream failure may return successfully while
committing typed recovery state and a handled ChildVault nonce; those committed
states are covered explicitly below.

Mid-execution state is not asserted. Functions with intentional transient state
include `closeEpoch`, rebalance lifecycle flows, inbound CCIP handlers, and
recovery execution.

Properties must hold under any sequence of valid external calls, including
reordering and reentrancy attempts, subject to the documented environmental
assumptions.

Use this verification vocabulary:

| Type            | Meaning                                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------------------- |
| `invariant`     | Holds globally between successful top-level calls and should be checked by a stateful invariant runner. |
| `postcondition` | Holds immediately after a specific function succeeds.                                                   |
| `unit`          | Deterministic test for an exact branch, authorization rule, or revert.                                  |
| `integration`   | Multi-contract, cross-chain, workflow, deployment, or upgrade test.                                     |
| `fv`            | Formal verification.                                                                                    |
| `manual`        | Auditor, operator, or release-process review.                                                           |

Properties exercised by the current stateful invariant suites are marked
`implemented: Foundry, Medusa, Recon-fuzzer` after passing all three runners. Unmapped properties
remain `revalidation pending`. Where the configured invariant topology is narrower than the full deployment
quantifier, the coverage cell states that narrower scope explicitly.

Use these ID prefixes:

| Prefix      | Category                                                        |
| ----------- | --------------------------------------------------------------- |

| `SOLV-*`    | Solvency and asset backing.                                     |

## External Assumptions

These assumptions are verified through workflow tests, integration or fork
tests, deployment checks, monitoring, or manual review. They are not pure
contract invariants.

| ID        | Statement                                                                                                                                                                                                                                                                                                                                                                    | Type                   | Coverage   |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ---------- |
| `ENV-001` | CRE-reported TVL is trusted. Incorrect TVL can corrupt epoch share accounting once claims begin. The workflow must not submit settlement TVL while a relevant recovery state makes that value incomplete or double-counted.                                                                                                                                                  | `manual + integration` | documented |
| `ENV-002` | CCIP provides the authenticated router callback, message uniqueness, ordered-delivery semantics requested by the sender, and the documented token-transfer behavior. Local recovery does not guarantee global CCIP liveness.                                                                                                                                                 | `manual + integration` | documented |
| `ENV-004` | Beyond the local safeguards in `ADAPTER-006` through `ADAPTER-009`, registered adapters and their underlying protocols faithfully implement the advertised asset, deposit, withdraw, and TVL semantics. Activation does not prove arbitrary adapter or protocol correctness.                                                                                                 | `manual + integration` | documented |
| `ENV-005` | For each ChildVault and nonce domain, CRE and CCIP are coordinated so a legitimate command is never delivered or executed after a higher nonce in that domain has already been accepted by that ChildVault.                                                                                                                                                                  | `manual + integration` | documented |
| `ENV-006` | Operators preserve every cross-chain route needed by an active strategy, pending rebalance, in-flight message, or outstanding settlement. Current setters permit unregistering routes and do not enforce this continuity onchain.                                                                                                                                            | `manual + integration` | documented |
| `ENV-007` | The rebalance workflow calls `completeRebalance` only after the complete rebalance amount has reached and been deposited into the target strategy, with no source withdrawal, CCIP delivery, target deposit, or relevant ChildVault recovery outstanding. ParentVault does not prove these offchain facts.                                                                   | `manual + integration` | documented |
| `ENV-008` | From before a cross-chain rebalance is sent until destination activation completes, the destination ChildVault's AdapterRegistry contains an adapter for the target protocol that is bound to that ChildVault. ParentVault can verify only global protocol support and the destination route.                                                                                | `manual + integration` | documented |
| `ENV-009` | The underlying asset implements usable ERC-20 metadata and exact accounting-compatible transfer semantics; `decimals()` is at most 77 so `10 ** decimals()` cannot overflow. Adapter construction additionally assumes the configured vault exposes the intended asset.                                                                                                      | `manual + deployment`  | documented |
| `ENV-010` | YieldcoinShare `MINTER_ROLE` and `BURNER_ROLE` are granted only to ParentVault. Role administration remains trusted not to grant supply-changing authority to any other account while shares back open intents or closed-epoch settlement. | `manual + deployment`  | documented |
| `ENV-011` | CRE, CCIP execution, and operators coordinate recovery-producing operations across the deployment so no new operation can create recovery on one chain while any ParentVault or ChildVault recovery remains active on another chain. Individual vault contracts enforce only their local recovery singleton.                                                                 | `manual + integration` | documented |

## Intentional Deviations

These are intentional behaviors, not invariant violations.

| ID        | Deviation                                                                                                                                     |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `DEV-001` | `YieldcoinShare.totalSupply()` may differ temporarily from `ParentVault.s_totalShares` because user claim minting and burning are lazy.       |
| `DEV-002` | During cross-chain `REBALANCING`, funds may be in transit and a vault may have `s_activeProtocolAdapter == address(0)`.                       |
| `DEV-003` | Dust withdraw claims may round down to zero asset. The intent is consumed and escrowed shares are burned without a zero-value asset transfer. |

## Non-Invariants

- `s_totalShares` is not monotonic.
- The implied TVL-to-share ratio is not monotonic.
- Token `totalSupply()` is not always equal to `ParentVault.s_totalShares`.
- TVL is not always observable on a single chain during cross-chain execution.
- The active adapter need not remain equal to the AdapterRegistry's current
  mapping after activation.
- User-facing and asynchronous functions are not expected to be revert-free.
- Strategy principal is not guaranteed; entitlement follows actual settled TVL.

## Third-Party Operations

`depositFor` and `withdrawFor` separate the account supplying tokens from the
beneficiary that owns the resulting epoch position. That funding is an
irrevocable transfer of economic ownership: only the beneficiary may cancel
the position and receive its refund. The permissionless claim functions may be
triggered by any caller but always route proceeds to the named position owner.

| ID        | Statement                                                                                                                                                                                                                                                                                                                                             | Type                        | Coverage             |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------- | -------------------- |
| `FOR-001` | Every successful `depositFor` debits exactly the requested underlying asset from the caller and increases only the beneficiary's current-epoch deposit entry and the epoch aggregate deposit amount by that amount.                                                                                                                                     | `postcondition + invariant` | implemented: Foundry, Medusa, Recon-fuzzer; Certora: dedicated direct rules |
| `FOR-002` | Every successful `withdrawFor` debits exactly the requested shares from the caller and increases only the beneficiary's current-epoch withdraw entry and the epoch aggregate share-burn amount by that amount.                                                                                                                                          | `postcondition + invariant` | implemented: Foundry, Medusa, Recon-fuzzer; Certora: dedicated direct rules |
| `FOR-003` | When the caller and beneficiary are distinct, successful `depositFor` and `withdrawFor` do not reduce the beneficiary's underlying-asset or share-token balance, respectively. The beneficiary supplies no allowance and no assets for the submitted position.                                                                                         | `postcondition`             | implemented: Foundry, Medusa, Recon-fuzzer; Certora: dedicated direct rules |
| `FOR-004` | A successful `claimSharesFor(user, epochNonce)` consumes only `user`'s deposit entry and mints the resulting shares only to `user`. When the caller and `user` are distinct, the caller receives no shares from the claim.                                                                                                                               | `postcondition + invariant` | implemented: Foundry, Medusa, Recon-fuzzer; Certora: dedicated direct rules |

| `FOR-007` | Third-party funding changes ownership without creating protocol value: modeled value removed from a distinct payer equals the new beneficiary entitlement, while aggregate deposit, share-escrow, authoritative-share, and solvency accounting remain governed by `SOLV-001`, `SOLV-003`, `SOLV-005`, `SOLV-006`, and `SHARE-003`.                       | `invariant`                 | implemented: Foundry, Medusa, Recon-fuzzer; Certora: dedicated direct accounting rules |

## Nonce Sequencing

### ChildVault

Each ChildVault has an epoch domain shared by inbound CCIP epoch deposits and
CRE-triggered epoch withdrawals, and a rebalance domain shared by inbound CCIP
rebalance deposits and CRE-triggered rebalance execution. The ordering guarantee
supporting sparse nonces is `ENV-005`.

| ID          | Statement                                                                                                                                                                                                                                                                                                                                                                    | Type               | Coverage                                                                                                                                                                         |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NONCE-001` | Each ChildVault initializes both high-water marks to zero. Epoch and rebalance domains are independent, and nonce state is independent between ChildVault instances.                                                                                                                                                                                                         | `unit + invariant` | implemented: Foundry, Medusa, Recon-fuzzer; Certora: direct initialization and domain-isolation rules; cross-instance isolation is architectural                                 |
| `NONCE-002` | Every successful modeled state transition leaves each ChildVault's epoch and rebalance high-water marks no lower than before the transition.                                                                                                                                                                                                                                 | `postcondition`    | implemented: Foundry, Medusa, Recon-fuzzer; Certora: direct parametric rules                                                                                                     |
| `NONCE-003` | All four nonce-bearing Child entry paths accept only a nonce strictly greater than the corresponding high-water mark. Zero, equal, and lower nonces revert; skipped values are permitted subject to `ENV-005`.                                                                                                                                                               | `unit`             | implemented: Foundry, Medusa, Recon-fuzzer; Certora: direct rules                                                                                                                |
| `NONCE-004` | Acceptance through CCIP or CRE updates the shared domain high-water mark and makes the same or any lower nonce invalid through both ingress paths. Handling one domain does not change the other.                                                                                                                                                                            | `invariant + unit` | implemented: Foundry, Medusa, Recon-fuzzer; Certora: direct + compositional parametric rules                                                                                     |
| `NONCE-005` | A full transaction revert, including a structural missing-adapter failure, rolls back a temporary nonce update and creates no recovery. A caught external failure that stores recovery and returns successfully commits the accepted nonce, so the original command cannot be submitted again as fresh work.                                                                 | `postcondition`    | implemented: Foundry, Medusa, Recon-fuzzer; Certora: direct rules + EVM atomicity                                                                                                |
| `NONCE-006` | A recovery created by a nonce-bearing operation stores that accepted nonce. | `NONCE-007` | The no-pending-recovery guard runs before nonce validation.
